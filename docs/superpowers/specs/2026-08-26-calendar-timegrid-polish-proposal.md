## 1. 배경과 목표

한솔 요청(2026-08-26):
1. 현재 주간 보기(카드 나열식)에 더해, 구글 캘린더처럼 **세로 시간축 위에 일정 블록을
   배치하는 친숙한 형식**을 추가.
2. 캘린더 전반의 보완점·UI 폴리싱·인터랙션 애니메이션을 프로 앱 수준으로.
3. (추가 질문) **외부 캘린더 구독** — 팀원들이 각자의 개인 캘린더와 연동하는 것까지 —
   이 오버 사이즈인지, 넣을 만한 크기인지 평가. → §7 참조.

1차 설계서 §2는 "주/일 보기의 시간표 축(hour grid)"을 **명시적 2차 예약 항목**으로 등재했다.
즉 시간표 추가는 기존 기획과 충돌하지 않는 예정된 다음 단계다.

## 2. 현황 진단 요약 (2026-08-26 코드 실사, HEAD=ab72175, 검증 리뷰 1회 반영)

7개 관점 병렬 조사 + 적대적 검증 리뷰를 거친 결과의 핵심.

### 2-1. 뷰 구조
- 팀 캘린더의 메인 뷰는 `src/views/ScheduleView.tsx`(1,067줄). `src/views/CalendarView.tsx`는
  별개의 "프로젝트 타임라인"(타임라인/히트맵/간트) 뷰이므로 혼동 주의.
- 뷰 모드 4종 `month | 2week | week | today` — **전부 시간축이 없는 카드/칩 방식**.
  주간(`WeekScrollView` 516줄)은 포커스 주 캐러셀 + 일정 카드 리스트, 오늘(`DayScrollView`)은
  5일 가로 캐러셀. 시각 일정은 어디서든 텍스트(`14:00 – 15:00 · 태그`)로만 표현된다.
- 월간(`CalendarGrid` 600줄)이 가장 완성도 높음: 멀티데이 바 패킹, 일 단위 드래그
  이동/리사이즈/생성, +N 더보기, 글라스 툴팁.

### 2-2. 데이터: 시간표의 재료는 이미 완비
- `CalendarEvent.allDay / startTime / endTime`("HH:MM", KST) — DB(`calendar_events.all_day/
  start_time/end_time`) → IPC 계약 → 타입 → 생성 모달(10분 단위 입력, +1h 자동 제안) →
  사이드패널 편집 → 정렬/포맷 유틸까지 전 구간 관통. **렌더 계층만 만들면 된다.**
- 주의: `allDay`는 tri-state. 렌더러 전역이 `allDay === false`일 때만 시각 일정으로 취급
  (undefined = 레거시/휴가 = 종일). 시간표도 동일 규칙을 따라야 한다.
- 구글 레이어 이벤트도 KST 시각을 온전히 갖고 들어온다(B flow가 만든 것만 편집 가능).
- 없는 것: 반복(recurrence) 개념 전무, 이벤트 개별 색 없음(캘린더 색 파생), viewMode/기간
  비영속(ScheduleView 로컬 state).

### 2-3. 인터랙션/모션
- DnD(`useCalendarDnD`)·드래그 생성(`useCalendarDragCreate`)은 **일 단위 + data-date 셀 기반 +
  월간 전용 + 마우스 전용**. 시간 스냅·세로 리사이즈·겹침 컬럼 배치·드래그 자동 스크롤은 신규.
- 낙관 반영/롤백은 `calendarService.updateEvent` 저장소별 분기에 이미 완비 — 세로 리사이즈의
  영속화 경로는 코드 추가 없이 준비됨.
- 모션 표준: easing `cubic-bezier(0.16,1,0.3,1)` + duration 계층(hover 100~150ms / 진입
  150~250ms / 뷰 전환 250~400ms), framer-motion(진입·퇴장·레이아웃) + CSS keyframes(무한 펄스).
- **reduced-motion**: CSS 계열은 `index.css:1032` 전역 킬스위치가 이미 커버한다. **누락
  구간은 framer-motion 경로**(뷰 전환·모달·QuickEdit 등 — JS 인라인 스타일이라 CSS
  오버라이드가 닿지 않음). `useMotionPref`(현재 my-tasks 전용, 소비처 1곳)를 공용 승격해
  framer 구간에 주입하는 것이 정확한 처방.

### 2-5. 프로 캘린더 리서치 요점 (Google/Notion Calendar/Fantastical/Amie/Vimcal/Rise)
- 표준 골격: 시간 거터 + 1시간 실선/30분 보조선 + **현재 시각 빨간 줄(오늘 컬럼 강조 + 거터
  시각 라벨) + 로드 시 현재 시각 자동 스크롤** + 상단 종일 레인(+N 접기) + **15분 스냅**.
- 겹침 배치: 충돌 클러스터 균등 분할(소규모 팀에 유리, 우측 빈 컬럼 확장 포함) vs Google식
  계단 캐스케이드. → **균등 분할 채택 권고**.
- 드래그 3종 세트(표준 취급): 원위치 고스트 + 블록 내 시간 라벨 실시간 갱신 + Esc 취소.
- 키보드 최소 셋: `T / W·M / ←→ / C / Esc / ?` — 이것만으로 프로 감각 대부분 확보.
- 뷰 전환 모션은 절제가 정답(즉시~200ms, 연타 시 스킵). 헤더·거터는 고정, 이벤트 레이어만 이동.
- 다크 블록: **색 15~30% 틴트 채움 + 좌측 2~3px 원색 레일 + 밝은 텍스트**(대비 4.5:1).
- 차별화 기회: Realtime로 "다른 팀원이 옮긴 블록이 눈앞에서 이동 + 하이라이트 펄스". §9-2의
  구현 전제(스냅샷 diff) 참조.

## 3. 제안 A — 주간 시간표(타임그리드) 보기 [핵심]

시안 §02 참조. 스펙 개요(확정은 Q1~Q2 결정 후 상세 설계서에서):

- **구성**: 좌측 시간 거터(오전/오후 라벨) + 7일 컬럼 + 1시간 실선/30분 보조선 + 상단 종일
  레인(최대 2~3행 + "+N개" 확장 토글) + 현재 시각 라인(오늘 컬럼 진하게 + 거터 시각 칩) +
  **0~9시 접힘 / 19~24시 접힘(해당 구간에 일정 있으면 자동 펼침) / 9~19시 기본 노출** +
  로드 시 현재 시각 근처 자동 스크롤 + 주말 컬럼 딤.
- **휠 정책(결정)**: 시간표 본체에서 휠 = 세로 시간 스크롤 전용. 주 이동은 `←→`/헤더
  화살표/Shift+휠로 분리한다. (현행 주간 뷰의 "휠=주 이동" 관례와 충돌하므로 명시 확정 필요)
- **블록**: 캘린더색 18% 틴트 + 좌 3px 레일 + `HH:MM` 라벨(기존 `formatEventTimeRange` 재사용),
  최소 높이(15분), 지난 일정 opacity 딤, 진행 중 일정 서브틀 강조.
- **접근성(필수 조건)**: 신규 시간표 블록은 `<button>` + `tabIndex` + `aria-label` 기반으로
  만들어 G10 부채를 늘리지 않는다. (기존 월 그리드 칩 개보수는 T2 유예 — §4)
- **읽기 전용 규칙**: `isReadOnly` 블록(구글 순수 유입분·권한 없는 공유분·휴가)은 드래그
  핸들·리사이즈 엣지 미부착 + `cursor: pointer`(월 그리드와 동일 관례).
- **겹침**: 충돌 클러스터 균등 분할 + 우측 확장. **순수 함수로 분리해 단위 테스트**(기존
  `layoutEventBars` 선례).
- **데이터 매핑 규칙**:
  - `allDay !== false` → 종일 레인 (tri-state 규칙 준수).
  - 멀티데이 timed(startDate ≠ endDate && allDay === false) → v1은 **종일 레인 강등 표시**
    (구글 유입 가능성 대비, 렌더 규칙 미정의 상태를 해소). 상세 설계 시 재확인.
- **인터랙션(단계 3)**: 빈 슬롯 드래그 생성(15분 스냅, 클릭=기본 30분, 라이브 시간 라벨) /
  블록 이동(요일+시간 2축, 원위치 고스트, Esc 취소) / 하단 엣지 리사이즈 / 드래그 중 가장자리
  자동 스크롤 / 드롭 안착 피드백(overshoot+플래시).
- **신규 코드 단위(예상)**: `WeekTimeGridView.tsx`(뷰) + `timeGridLayout.ts`(겹침·픽셀↔분 스냅
  순수 유틸 + 테스트) + `useTimeGridDnD.ts`(시간 스냅 드래그 훅) +
  `calendarEventDiff.ts`(Realtime 하이라이트용 전후 스냅샷 비교 — §9-2). 기존 재사용:
  정렬/포맷 유틸, EventCreateModal(시각 프리필만 추가), EventSidePanel/QuickEdit, 낙관 저장
  경로, identity 유틸, glassStyles, TRANSITION 관례.
- **선행 리팩터링(권고)**: ScheduleView 내 viewMode 분기 8곳(기간 계산/네비/키보드/헤더 라벨/
  사이드바/본체 JSX)을 뷰별 정책 객체로 추출해 새 모드 추가 비용을 낮춘다.

## 5. 제안 C — UI 폴리싱

- 월 그리드: **시각 일정 = 점+시각 텍스트 라인, 종일/기간 일정만 바** (시안 §04). 부수 효과로
  칸당 표시 개수 증가. maxVisibleBars 죽은 분기·stale 주석 정리(G9).
  - **주의(체급 경고)**: 현행 월 그리드의 드래그·+N·행 패킹이 전부 "바" 기준이다
    (`layoutEventBars`, pointer-events 우회, overflowCount). 점 라인 전환 시 ① 시각 일정의
    일 단위 드래그 이동 경로를 점 라인에도 유지하고 ② `layoutEventBars` 입력을 종일/기간으로
    좁히고 ③ 칸 표시 한도를 바 행+점 라인 2계층으로 재설계해야 한다. 단순 스타일 교체가
    아니므로 단계 4에서 별도 커밋으로 다루고, 부담스러우면 이 항목만 다음 라운드로 미룬다.
- 생성 모달 백드롭: `bg-black` 추가 + 농도 통일(무딤이 의도였는지 한솔 확인 후).
- 빈 상태 통일(월 그리드 전용 빈 상태 부재), '오늘' 버튼 펄스 전 뷰 적용.

## 7. 제안 E — 외부 캘린더 구독 검토 (한솔 추가 질문, 2026-08-26)

질문: "외부 캘린더를 구독하는 기능까지 추가하는 건 오버인지, 넣을 만한 사이즈인지.
팀원들이 각자의 개인 캘린더와 연동하는 것까지 생각 중."

### 7-1. 먼저, 이미 되는 것
**각 팀원이 자기 구글 캘린더를 연동하는 기능은 이미 있다.** 팀 공용 OAuth 클라이언트가 앱에
내장되어(`electron/googleCalendar.ts:20-23`, 의도된 하드코딩 — 슬랙 웹훅과 같은 내부 툴 정책)
팀원 누구나 설정에서 버튼 한 번으로 본인 구글 계정을 연결할 수 있고, 토큰은 각자 PC에
암호화 저장(safeStorage), 구글 일정은 **본인 화면에만** 레일 "내 구글" 레이어로 표시된다
(로컬 캐시 — Supabase에 올라가지 않음). 비개발자 팀원들이 이 기능의 존재를 모를 수 있으니
안내만으로도 절반은 해결된다.

### 7-2. 옵션별 사이즈 평가
| 옵션 | 내용 | 사이즈 판정 |
|---|---|---|
| **E1. 주소(ICS) 구독** | 애플·네이버·아웃룩·구글 모두 "캘린더 공유 → 주소(iCal/ICS URL)"를 제공한다. 이 주소를 등록하면 읽기 전용 레이어로 겹쳐 보이는 기능. 제공자별 로그인 연동 없이 **하나의 구현으로 사실상 모든 외부 캘린더를 커버**. 메인 프로세스 주기 fetch(+수동 새로고침), ICS 파서(node-ical류)로 반복 일정을 "앞으로 N개월 전개"해 읽기 전용 인스턴스로 캐시, 레일에 "구독" 섹션, 구독 목록은 나만 보기(로컬 저장). | **넣을 만한 사이즈 — 중형 PR 1개.** 복잡점은 RRULE(반복) 전개와 시간대 처리인데 검증된 파서 라이브러리로 해결 가능. 이번 로드맵의 선택 단계 5로 수용 가능 |
| **E2. 팀원 개인 캘린더를 서로 보기** | 각자의 개인 일정이 팀원 화면에도 겹쳐 보이는 기능(구글 "함께 보기"급). 현재 구글 데이터는 각자 PC 로컬 전용이라, 하려면 개인 일정을 Supabase로 올려 공유해야 한다 → 프라이버시 설계(제목 공개 vs "바쁨"만 표시), 팀원별 동의 UX, 각자 PC가 소스인 데서 오는 동기화 공백(꺼진 PC = 갱신 중단), 연동 해제·삭제 경로까지 전부 신규 설계. | **오버 — 별도 기획 라운드 권고.** 이번에 끼우면 시간표 본체가 밀린다. 필요하면 다음 라운드에서 "바쁨만 공유" 최소안부터 기획 |
| E3. 제공자별 직접 로그인 연동(애플·네이버·아웃룩 OAuth/CalDAV) | 제공자마다 인증·API가 제각각 | **불필요** — E1(주소 구독)이 동일 효용을 훨씬 싸게 커버 |

### 7-3. 권고
- **E1은 Q5로 결정** — 포함 시 로드맵 선택 단계 5(v1.110 예정)로 뒤에 붙인다(시간표 본체와
  파일 겹침 거의 없음: 신규 파서/스토어 + 레일 섹션 추가 위주).
- E2는 이번 범위에서 제외하고, 원하면 별도 라운드로 기획(1차 캘린더 설계서의 권한 모델과
  프라이버시 원칙 — "개인 캘린더는 admin도 관리 불가" — 을 그대로 존중해야 하는 사안).
- E1 채택 시 상세 설계에서 확정할 것: 구독 주소의 저장 위치(로컬 vs 계정), 새로고침 주기,
  일정 수 상한, 시간표/월/카드 뷰 전 표면 표시 규칙(읽기 전용 스타일).

## 9. 리스크와 조율 사항

1. **1차 잔여분(알림) 파일 겹침**: 알림 작업과 시간표 작업이 `ScheduleView.tsx`/
   `calendarService.ts`/`App.tsx`를 공유 — Q3=A로 리베이스 비용 최소화.
2. **Realtime 하이라이트 펄스의 구현 전제**: 현행 realtime 계층은 의도적으로 행 데이터를
   버리고 `eventType`만 전달한다(`electron/realtime.ts:15-21,163` — 무효화 신호 설계).
   따라서 "어느 일정이 바뀌었나"는 **렌더러의 정본 재조회 전후 스냅샷 diff**로 식별한다
   (`calendarEventDiff.ts` 신설, identity 기준 비교). realtime 계약 변경은 하지 않는다.
3. **CalendarWidget 미반영**: 위젯(842줄)은 완전 별도 구현이라 새 뷰가 자동 반영되지 않음
   (T2로 명시 수용). 팝업 경로 회귀는 캐릭터 보드 교훈대로 배포 전 점검.
4. **KST 전제**: 시각 계산은 기존 `+09:00` 하드코딩 전제를 그대로 따른다(팀 단일 시간대).
   E1(ICS 구독) 채택 시 외부 피드의 TZID 처리도 KST 변환으로 통일.
5. **allDay tri-state / 멀티데이 timed**: §3 매핑 규칙을 상세 설계서에서 최종 확정.
6. **월 그리드 점 라인 전환(제안 C)의 체급**: §5 주의 참조 — 드래그·패킹·+N 재설계 동반.
7. **calendarService 비대(2,875줄)**: 이번 범위에서는 분해하지 않고 T2 후보로만 기록.

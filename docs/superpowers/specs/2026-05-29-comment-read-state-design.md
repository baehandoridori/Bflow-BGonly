# 댓글 읽음 상태 UX 디자인

> 작성일: 2026-05-29  
> 대상: 씬 뷰 카드/시트, 피드백 허브, 씬 상세 모달 댓글 및 활동 탭  
> 확인 목업: [docs/mockups/2026-05-29-feedback-comment-unread-final-check.html](../../mockups/2026-05-29-feedback-comment-unread-final-check.html)

## 1. 배경

씬 카드, 시트, 피드백 허브에서 댓글이 있는지는 보이지만, 내가 이미 확인한 댓글인지 새로 생긴 댓글인지 구분이 약했다. 사용자는 Slack의 안읽은 메시지처럼 “새 댓글이 생겼고, 내가 확인하면 조용히 사라지는” 흐름을 원한다.

이번 설계는 댓글 알림을 과하게 키우지 않고, 기존 B flow 다크 UI 톤 안에서 다음을 해결한다.

- 새 댓글이 있는 씬을 카드/시트/피드백 허브에서 즉시 알아보기
- 상세 모달을 열면 새 댓글 위치를 바로 찾기
- 내가 확인한 뒤에는 같은 PC가 아니어도 읽음 상태 유지
- 일반 댓글과 리비전 댓글을 한 흐름으로 다루기

## 2. 최종 결정

| 항목 | 결정 |
|---|---|
| 읽음 저장 위치 | Supabase |
| 저장 단위 | 사용자 + 씬 단위 마지막 확인 시간 |
| 댓글 범위 | 일반 댓글 + 리비전 댓글을 같은 씬 흐름으로 합산 |
| 내 댓글 처리 | 내가 쓴 댓글은 나에게 안읽음으로 만들지 않음 |
| 카드/시트/허브 배지 숫자 | 전체 댓글 수 유지 |
| 안읽음 표현 | 댓글 SVG 아이콘 + 숫자 배지만 보라색 펄스 |
| 읽음 표현 | 같은 배지를 회색 톤으로 표시 |
| 상세 모달 진입 | 첫 안읽은 댓글 위치로 자동 이동 |
| 상세 모달 구분선 | `새 댓글` |
| 읽음 처리 시점 | 첫 안읽은 댓글 위치가 화면에 보이는 순간 |
| 저장 실패 처리 | 화면은 읽음처럼 처리하고 백그라운드 재시도 |
| 이번 범위 제외 | 새 댓글 필터, 새 댓글 우선 정렬 |

## 3. UX 상세

### 3-1. 카드뷰/시트뷰 댓글 배지

댓글 배지는 기존 디자인 톤을 유지해 `MessageCircle` 계열 SVG 아이콘과 숫자로 구성한다. 실제 이모지는 쓰지 않는다.

- 안읽음 있음: 보라색 배지, 조용한 pulse
- 읽음 상태: 회색 배지
- 숫자: 전체 댓글 수
- 예: 댓글 총 7개 중 새 댓글 2개여도 숫자는 `7`

카드나 행 전체는 펄스하지 않는다. 피드백 허브의 세로 라이트나 상태 색상과 섞이지 않게 댓글 배지만 신호를 맡는다.

### 3-2. 피드백 허브

피드백 허브의 리비전 카드도 같은 씬 읽음 상태를 사용한다. 피드백 허브에서 a001 리비전 댓글을 확인하면, 씬 뷰의 a001 댓글 배지도 읽음으로 내려간다. 반대로 씬 상세 모달에서 a001 댓글을 확인해도 피드백 허브의 a001 배지가 읽음으로 내려간다.

피드백 허브는 리비전 중심 화면이지만, 댓글 읽음 상태는 “씬의 대화 흐름” 기준으로 공유한다.

### 3-3. 씬 상세 모달

씬 상세 모달의 `댓글 및 활동` 탭은 새 댓글이 있으면 첫 안읽은 댓글 위치로 자동 스크롤한다.

구분선은 짧게 `새 댓글`로 표시한다. 구분선 아래의 새 댓글들은 처음 진입 시에만 살짝 강조한다. 읽음 처리 후에도 현재 모달 안에서는 구분선 위치를 유지해 사용자가 어디부터 새 댓글이었는지 알 수 있게 한다.

읽음 처리는 첫 안읽은 댓글 위치가 화면에 실제로 보이는 순간 실행한다. 구현은 `IntersectionObserver` 또는 동등한 viewport 감지 방식으로 한다. 모달을 열었지만 댓글 영역이 렌더링되지 않았거나 탭이 열리지 않은 경우에는 읽음 처리하지 않는다.

저장할 `last_read_at`은 현재 시각이 아니라, 그 순간 화면에 로드되어 있던 “다른 사람이 쓴 최신 댓글의 `createdAt`”으로 한다. 이렇게 해야 모달이 열린 직후 새 댓글이 동시에 도착해도, 사용자가 실제로 보지 않은 댓글까지 읽음 처리하지 않는다.

### 3-4. 답글/댓글 클릭

사용자가 안읽은 댓글을 클릭하거나 답글을 달아도 읽음 처리된다. 단, 상태 변경이나 리비전 진행/완료 버튼 클릭만으로는 댓글 읽음 처리하지 않는다.

## 4. 데이터 모델

### 4-1. 저장 방식

댓글 하나마다 읽음 row를 만들지 않는다. Supabase에는 사용자별, 씬별 마지막 확인 시간만 저장한다.

```sql
CREATE TABLE comment_read_states (
  user_id TEXT NOT NULL,
  scene_thread_key TEXT NOT NULL,
  last_read_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, scene_thread_key)
);
```

`scene_thread_key`는 댓글과 리비전을 하나의 씬 대화 흐름으로 묶기 위한 안정 키다. 원칙은 `EP:part:normalizedSceneId` 형태를 사용한다.

예:

```text
EP05:A:a001
EP05:B:b003
```

기존 일반 댓글은 `sheetName:sceneNo` 기반으로 저장되어 있으므로, 읽음 상태 계산 전에 현재 파트 메타데이터로 `sceneNo -> sceneId -> normalizedSceneId` 변환을 한다. 리비전은 이미 `revisionService`의 sceneKey 계열 규칙을 쓰므로 같은 정규화 규칙으로 합류시킨다.

씬 키를 만들 수 없는 로컬/프리뷰 상황에서는 기존 `sheetName:sceneNo` 키를 fallback으로 사용하되, Supabase 저장 대상은 안정 키를 우선한다.

### 4-2. 안읽음 계산

안읽음 여부는 다음 기준으로 계산한다.

1. 해당 씬의 일반 댓글과 리비전 댓글을 합친다.
2. 현재 사용자 본인이 작성한 댓글은 제외한다.
3. 남은 댓글 중 `createdAt > lastReadAt`인 댓글이 하나라도 있으면 안읽음이다.

편집된 댓글의 `editedAt`은 이번 범위에서는 안읽음 기준에 넣지 않는다. 댓글 내용 수정까지 새 알림으로 다루면 알림 기준이 과해질 수 있기 때문이다.

## 5. 프론트엔드 구조

### 5-1. 서비스

새 서비스 API:

```ts
getCommentReadStates(userId: string): Promise<Record<string, string>>
markSceneThreadRead(input: {
  userId: string;
  sceneThreadKey: string;
  readAt: string; // 화면에 보인 다른 사용자 최신 댓글 createdAt
}): Promise<void>
isSceneThreadUnread(input: {
  latestOtherUserCommentAt?: string;
  lastReadAt?: string;
}): boolean
```

화면은 먼저 로컬 상태를 즉시 갱신하고, Supabase 저장은 뒤에서 수행한다.

### 5-2. 백그라운드 재시도

읽음 저장이 실패해도 사용자에게 경고 토스트를 띄우지 않는다. UI는 읽음 상태로 유지한다.

실패한 저장은 메모리 큐에 넣고 다음 시점에 재시도한다.

- 같은 앱 세션 안에서 10초 후 1차 재시도
- 1차 실패 시 30초 후 2차 재시도
- 2차 실패 시 다음 댓글/읽음 상태 로드 때 한 번 더 재시도
- 앱 종료 후 영구 큐는 이번 범위에서 제외

### 5-3. 화면별 사용

| 화면 | 사용 방식 |
|---|---|
| SceneCard | 댓글 배지 색상/펄스 |
| SceneSheetView | 댓글 배지 색상/펄스 |
| UnifiedSceneCard | BG/ACT 합산 댓글 중 안읽음 있으면 펄스 |
| UnifiedSceneSheetView | 합산 댓글 배지에 안읽음 상태 반영 |
| FeedbackHub | 리비전 카드 댓글 배지에 같은 씬 읽음 상태 반영 |
| CommentPanel | 첫 안읽은 댓글 위치에 `새 댓글` 구분선, viewport 진입 시 읽음 처리 |

## 6. 접근성 및 디자인 원칙

- 아이콘은 SVG를 사용하고 실제 이모지는 쓰지 않는다.
- 배지 펄스는 2.4~2.8초 정도의 느린 pulse로 제한한다.
- `prefers-reduced-motion` 사용자는 pulse를 끄고 색상 차이만 제공한다.
- 배지에는 `title` 또는 `aria-label`로 `새 댓글 포함, 전체 댓글 N개` / `확인한 댓글, 전체 댓글 N개`를 제공한다.
- 새 댓글 구분선은 텍스트만으로도 의미가 전달되어야 한다.

## 7. 범위 제외

이번 작업에 포함하지 않는다.

- 새 댓글 있음 필터
- 새 댓글 우선 정렬
- 댓글별 개별 읽음 상태
- 댓글 편집을 새 댓글처럼 다시 띄우기
- 앱 종료 후 재시도 큐 영구 저장
- 댓글 읽음 상태를 Slack/외부 알림과 동기화

## 8. 테스트 기준

### 사용자 확인

1. 다른 사람이 새 댓글을 남기면 카드/시트/피드백 허브 댓글 배지가 보라색으로 펄스된다.
2. 배지 숫자는 전체 댓글 수를 유지한다.
3. 씬 상세 모달을 열면 첫 새 댓글 위치로 이동하고 `새 댓글` 구분선이 보인다.
4. 새 댓글 위치가 화면에 보이면 배지가 회색으로 바뀐다.
5. 같은 씬은 씬 뷰와 피드백 허브에서 같은 읽음 상태를 공유한다.
6. 내가 쓴 댓글은 나에게 새 댓글로 뜨지 않는다.

### 개발자 검증

1. `isSceneThreadUnread`는 `latestOtherUserCommentAt > lastReadAt`일 때만 true를 반환한다.
2. 본인 댓글만 있는 씬은 안읽음이 되지 않는다.
3. `markSceneThreadRead`는 같은 `user_id + scene_thread_key`를 upsert한다.
4. 저장되는 `last_read_at`은 현재 시각이 아니라 화면에 보인 다른 사용자 최신 댓글의 `createdAt`이다.
5. 저장 실패 시 UI 상태는 롤백되지 않고 재시도 큐에 들어간다.
6. `CommentPanel`은 첫 안읽은 댓글 위에 구분선을 한 번만 렌더링한다.
7. `prefers-reduced-motion` 환경에서 pulse 애니메이션이 비활성화된다.

## 9. 구현 순서 초안

1. Supabase 읽음 상태 테이블 및 IPC/service 경로 추가
2. 댓글/리비전 댓글을 씬 thread 단위로 모으는 helper 추가
3. 카드/시트/피드백 허브 배지에 읽음 상태 연결
4. CommentPanel에 `새 댓글` 구분선과 자동 스크롤 연결
5. viewport 진입 시 optimistic read + Supabase upsert 연결
6. 실패 재시도 큐 추가
7. 테스트 및 실제 앱 프리뷰 확인

이 문서는 구현 계획이 아니라 확정된 UX/데이터 설계다. 실제 파일별 작업 순서는 별도 implementation plan에서 세분화한다.

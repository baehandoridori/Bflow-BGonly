# Update Notes Design

**Goal:** 좌하단 버전 버튼에서 보이는 업데이트 내역을 팀원이 빠르게 이해할 수 있는 C+A 혼합형 기록으로 정리하고, 과거 PR 내역은 큰 릴리스 중심으로 복원한다.

**Decision:** 앱 안 업데이트 내역은 "카테고리 -> 짧은 요약 -> 작은 설명" 구조를 쓴다. 기술 상세, 파일명, 함수명, 원인 분석은 PR 본문에 남긴다.

---

## Current State

- 원본 파일은 `DEVLOG/update-notes.json`이다.
- 빌드 시 `scripts/generate-manifest.js`가 이 파일을 읽어 `dist/manifest.json.releaseNotes`에 넣는다.
- 앱의 `UpdateCenterModal`은 `releaseNotes`를 받아 버전별 타임라인으로 보여준다.
- 현재 저장된 앱 내 업데이트 내역은 `v1.22.10`부터 `v1.23.3`까지다.
- PR 기준 최신 누락은 `v1.23.4` / PR #91이다.
- `v1.22.9` 이전의 과거 PR들은 앱 내 업데이트 내역으로 아직 복원되지 않았다.

## Writing Rule

업데이트 내역은 사용자가 "그래서 내가 뭘 체감하나"를 먼저 알 수 있어야 한다.

### Category

고정 카테고리는 아래 6개를 쓴다. 앱에는 해당 버전에 실제로 필요한 카테고리만 표시한다.

| ID | Label | Use |
| --- | --- | --- |
| `feature` | 기능 추가 | 새로 없던 기능이 생겼을 때 |
| `change` | 기능 수정 | 기존 기능의 동작 방식이 바뀌었을 때 |
| `bugfix` | 버그 수정 | 깨짐, 오동작, 회귀를 고쳤을 때 |
| `ux` | 사용성 개선 | 화면 읽기, 클릭 흐름, 표시 방식을 더 편하게 만들었을 때 |
| `stability` | 안정화 | 업데이트, 동기화, 저장, 실행 안정성을 높였을 때 |
| `docs` | 문서/운영 | 운영 문서, 배포 기준, 내부 기록을 정리했을 때 |

### Item Shape

각 항목은 두 줄 구조로 쓴다.

```json
{
  "category": "bugfix",
  "summary": "댓글 입력 안정화",
  "description": "긴 댓글을 써도 전송 버튼과 첨부 버튼이 화면 밖으로 밀리지 않습니다."
}
```

- `summary`는 C안처럼 짧게 쓴다.
- `description`은 A안처럼 사용자가 체감하는 설명을 한 문장으로 쓴다.
- 버전당 기본 3~5개 항목만 둔다.
- 큰 기능 릴리스도 5개를 넘기지 않는다. 넘치는 기술 내용은 PR 본문으로 보낸다.
- "root cause", `flex`, `overflow`, 함수명, 파일명 같은 개발자 표현은 앱 내 업데이트 내역에 쓰지 않는다.
- 검증용 배포처럼 사용자 기능 변화가 작으면 "업데이트 적용 안정화"처럼 목적을 명확히 쓴다.

### Note Shape

향후 `DEVLOG/update-notes.json`의 권장 형태는 아래와 같다.

```json
{
  "version": "1.23.4",
  "title": "댓글과 최근 작업 차트 표시를 다듬었습니다",
  "items": [
    {
      "category": "bugfix",
      "summary": "댓글 입력 영역 안정화",
      "description": "댓글이 많이 쌓인 상태에서도 입력창과 전송 버튼이 패널 안에 안정적으로 보입니다."
    },
    {
      "category": "feature",
      "summary": "활동 감추기 추가",
      "description": "댓글 패널에서 단계 변경 같은 활동 기록을 숨기고 댓글만 볼 수 있습니다."
    },
    {
      "category": "change",
      "summary": "선 그래프를 직선으로 변경",
      "description": "최근 작업 차트의 선 그래프가 더 명확한 직선 형태로 표시됩니다."
    }
  ]
}
```

## Compatibility

기존 `items: string[]` 형식은 바로 깨뜨리지 않는다.

- `UpdateReleaseNote.items`는 구현 시 문자열과 객체를 모두 받을 수 있게 정규화한다.
- 문자열 항목은 임시로 `{ category: 'change', summary: item, description: '' }`처럼 보여준다.
- 새로 작성하거나 백필하는 항목은 모두 객체 형식을 사용한다.
- `generate-manifest.js`는 객체 항목을 보존하고, 예전 문자열 항목도 계속 통과시킨다.

비개발자 설명: 지금까지는 업데이트 메모가 "문장 목록"이었다면, 앞으로는 "분류가 붙은 작은 카드 목록"이 된다. 예전 메모도 일단 계속 보이게 두고, 새 메모부터 새 방식으로 쌓는다.

## Backfill Strategy

과거 PR 복원은 A안으로 진행한다.

- 최신 누락 `v1.23.4`는 개별 버전으로 즉시 추가한다.
- `v1.22.10` 이후 현재 기록은 새 규칙에 맞춰 문장을 줄이고 카테고리를 붙인다.
- `v1.22.9` 이전은 모든 PR을 1:1로 넣지 않는다.
- 같은 목적의 hotfix와 검증 PR은 큰 릴리스 카드 안에 묶는다.
- 과거 내역은 사용자가 볼 가치가 큰 변화 위주로 남긴다.

## UI Direction

업데이트 모달은 현재 PR 타임라인 구조를 유지하되, 각 버전 카드 안의 항목을 카테고리별 작은 블록으로 보여준다.

- 카테고리 라벨은 항목 상단에 작게 표시한다.
- `summary`는 굵게 표시한다.
- `description`은 더 작은 글씨와 보조 색으로 표시한다.
- 카테고리별 색은 앱 디자인 토큰을 우선 사용하고, 과한 장식은 피한다.

## Acceptance Criteria

- 좌하단 버전 버튼의 업데이트 내역에서 C+A 구조가 보인다.
- `DEVLOG/update-notes.json`에 새 항목을 추가할 때 카테고리, 요약, 설명 규칙이 명확하다.
- 예전 문자열 형식 release note도 앱에서 깨지지 않는다.
- `v1.23.4`가 누락되지 않는다.
- 과거 PR은 큰 릴리스 중심으로 복원되어 모달이 지나치게 길어지지 않는다.
- `npm run typecheck`, 관련 자동 업데이트 테스트, `npm run build:vite`를 통과한다.

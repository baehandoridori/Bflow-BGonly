## 4. 계획서와 달라진 지점

계획서 밖 기능 추가나 리팩터링은 하지 않았다. 아래는 실제 코드·도구 상태와 맞추기 위해 필요했던 최소 조정과 검증 차이다.

### 4-1. 라인 번호와 앵커

- `CharacterCard.tsx`의 대상 블록은 계획서 187행이 아니라 실제 186행 부근에 있었다.
- `CharacterBoardTabs` 관련 추가 위치는 계획서 126행이 아니라 실제 파일 끝 125행 부근이었다.

### 4-2. 작업 3의 Node 22 직접 실행과 TypeScript import

계획서의 `./workFileIndex` 확장자 없는 import는 번들러에서는 맞지만, 계획서가 함께 지정한 Node 22의 TypeScript 직접 실행에서는 모듈을 찾지 못했다. 허용된 `sceneLinkIndex.ts` 안에서만 `./workFileIndex.ts`로 명시하고, 번들러 타입 검사에는 의도를 설명하는 `@ts-expect-error TS5097` 한 줄을 붙였다. 기능 범위는 바뀌지 않았다.

### 4-3. 기존 `byScene` 직접 소비자 호환

계획서는 프레즌스 저장소를 `byKind.scene`/`byKind.characterCostume`으로 일반화하면서 `byScene`을 제거하도록 기술했지만, 실제 코드의 `SceneSheetView.tsx`와 `UnifiedSceneSheetView.tsx`가 아직 `byScene`을 직접 구독하고 있었다. 이를 그대로 제거하면 기존 씬 편집자 표시가 깨지므로, 허용된 저장소 파일 안에서 `byKind.scene`을 가리키는 최소 호환 미러를 유지했다.

### 4-4. 현재 저장소 스키마·테스트 등록·미리보기 포트

- 계획서의 업데이트 내역 예시는 오래된 `summary`/`description[]` 형태였지만, 실제 자동 업데이트 코드는 `title`/`items[]`를 요구한다. 현재 스키마를 따르되 문구는 계획서의 비개발자 톤 규칙을 지켰다.

### 4-6. 배포 산출물 생성과 G드라이브 동기화

정식 `npm run build`는 exit 0이었지만 `latest.yml`이 없었다. 기본 `package.json`에 publish 설정이 없어 plain `electron-builder`가 업데이트 메타데이터를 만들지 않은 것이 첫 원인이었다. `--publish never`로 메타데이터 생성을 강제했을 때는 `electron-builder@24.13.3`이 이 worktree의 `.git` 포인터 파일에서 GitHub owner/repo를 자동 추론하지 못해, 두 값을 명시해야 했다. `--publish never`이므로 외부 게시나 업로드는 수행되지 않았다.

소스나 `package.json`은 바꾸지 않았다. Vite로 `dist`를 먼저 깨끗이 다시 만든 뒤 아래처럼 업로드 금지와 GitHub 저장소 정보를 명시해 패키징하고 manifest를 다시 생성했다.

```powershell
npx.cmd vite build
npx.cmd electron-builder --publish never `
  --config.publish.provider=github `
  --config.publish.owner=baehandoridori `
  --config.publish.repo=Bflow-BGonly
node scripts/generate-manifest.js
```

첫 진단 재실행에서는 저장소 소유자·이름을 생략해 메타데이터 생성이 실패했고, Vite 정리 없이 패키저만 반복하면 출력 `dist`가 입력에 다시 포함돼 설치 파일이 약 200MB에서 약 400MB로 커지는 문제도 확인했다. 남은 압축 프로세스를 해당 PID로만 종료하고, 깨끗한 Vite 빌드부터 다시 시작해 정상 크기 200,837,236바이트로 복구했다.

G드라이브에서는 `/MIR /XF manifest.json` 복사가 20분 감시 제한 뒤에도 종료되지 않았다. 내용 복사는 완료됐지만 G드라이브가 수정 시각을 다시 기록해 확인 재실행에서도 같은 파일을 복사 대상으로 보는 특성이 원인이었다. `/FFT /L` 감사 결과 mismatch 0 / failed 0 / extra 0이었고, 실제 파일 수·크기를 경로별로 비교했다.

첫 manifest 교체 뒤 전체 용량 검사에서 아래 한 파일이 0바이트인 것을 발견했다.

- `win-unpacked/resources/app/node_modules/@tiptap/react/src/useEditor.ts`: 원격 0바이트 → 정상 12,649바이트

독립 감사에서 확인했지만 계획서 밖이라 수정하지 않은 후속 위험:

- 프레즌스 복장 경로 캐시는 재연결 시 자동 새로고침되지 않는다.
- 복장 경로 새로고침이 동시에 겹치면 늦게 끝난 오래된 요청이 최신 값을 덮을 수 있다.

- 작업 5의 계획서 지정 테스트는 연결 문자열 존재를 확인하지만 호출 순서·횟수까지 고정하지는 않는다. 현재 구현은 계획 블록과 일치한다.

계획서 부록 C의 범위 외 후속 권장도 이번 회차에서는 손대지 않았다.

## 계획서와 실제 코드가 달랐던 지점

**1. 브랜치 베이스 — PR A 미머지 상태로 스택.**
계획서 4절은 PR B 를 "PR A 머지 후 main 에서 분기"하라고 지시한다. 그러나 PR 머지는 한솔 승인 사항이므로(저장소 관행), 승인 없이 머지하지 않고 **PR A 브랜치 위에 쌓아 PR B 의 base 를 `fix/feedback-34-40` 으로 지정**했다. GitHub 는 PR A 가 머지되면 PR B 의 base 를 자동으로 `main` 으로 재지정한다. 계획서가 요구한 "작업 9 의 before 는 작업 5 완료 상태" 전제는 그대로 충족된다.

**2. `characterTabGroups.ts` 의 `./createUuid` import 에 명시적 `.ts` 확장자 필요.**
계획서 8-2 는 "상대 경로로 import"만 지시했는데, `node --test` 의 ESM 해석은 확장자를 보완해 주지 않아 `ERR_MODULE_NOT_FOUND` 로 테스트가 통째로 실패했다(실제 재현 후 발견). 저장소에 이미 같은 상황의 관행이 있고(`src/features/playground/arcade/domain.ts` 등이 `'./constants.ts'` 로 import), `tsconfig.json` 에 `allowImportingTsExtensions: true` 가 켜져 있어 `'./createUuid.ts'` 로 고쳤다. typecheck·build 모두 영향 없음.
→ **다음 회차 계획서: "node --test 가 직접 import 하는 유틸의 상대 import 는 `.ts` 확장자 명시" 를 6절 리스크 5 에 추가할 것.**

**3. `package-lock.json` 버전 동반 갱신** — PR A 에서 이미 발견한 계획서 작업 7/10 공통 누락분. `tests/playgroundMarketUiWiring.test.ts` 가 `package.json` 과의 일치를 단언한다. 동일하게 처리.

그 외 작업 8·9 의 전제는 전부 실파일과 일치했다. 특히 계획서가 "파일에서 확인 후 미러할 것"으로 남긴 `applyCharacterUpdate` 의 시그니처는 예측대로 **모듈 레벨 함수 + `(set, get, ...)` 주입 + 비함수형 `set`** 이었고, `receiveRealtime` 은 `if` 체인 + `return` 스타일이어서 계획서의 분기 코드가 그대로 동형으로 들어갔다. `createUuid` 의 export 명도 계획서 예상대로였다.

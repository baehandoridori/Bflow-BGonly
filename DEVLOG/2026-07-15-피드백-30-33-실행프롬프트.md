# 피드백 30~33 실행 프롬프트 (구현 에이전트용)

> 아래 코드 블록을 구현 에이전트(코덱스·오푸스·다른 Claude 세션)에 그대로 붙여넣는다.
> 계획서가 자기완결적이므로 프롬프트는 문서를 가리키고 규율을 재강조하는 역할만 한다 — 계획 내용을 여기 중복 요약하지 않는다(요약본과 원문이 어긋나면 두 개의 진실이 생긴다).

```text
C:\Bflow-BGonly 저장소에서 피드백 수정 작업을 수행해줘.

**유일한 사양 문서: `C:\Bflow-BGonly\DEVLOG\2026-07-15-피드백-30-33-수정계획.md`**
(이 파일이 없으면 계획서 PR이 아직 머지되지 않은 것이다 — 진행하지 말고 보고할 것.)

이 문서는 자기완결적이며 독립 리뷰 3패스를 거쳤다. 문서를 처음부터 끝까지 읽고, 명시된 작업 순서(작업 1→7)대로 구현할 것.

규칙:
1. 계획서의 **절대 규칙**을 따른다 — 문서에 명시되지 않은 리팩터링·포맷 변경·기능 추가 금지. 수정 범위는 명시된 파일·블록으로 한정.
2. 라인 번호가 어긋나면 병기된 **앵커(고유 코드 조각)** 검색으로 위치를 재확정한다. 앵커도 못 찾으면 임의 진행하지 말고 해당 작업을 건너뛰고 마지막에 보고한다.
3. 각 작업의 **before 블록과 실제 코드가 다르면** 그 작업을 중단하고 차이를 보고한다 (스냅샷 이후 코드가 변경된 신호다).
4. 작업당 커밋 1개, 커밋 메시지는 한글(각 작업의 완료 기준에 예시가 있다). 계획서가 지정한 테스트 갱신·추가를 코드 수정과 **같은 커밋**에 포함한다.
5. 각 작업 완료 시 그 작업의 '검증 방법'을, 전체 완료 시 부록 B-1 전체 검증을 실행하고 결과 수치를 기록한다.
6. 버전 번호는 계획서 4절 정책대로 **구현 착수 시점의 origin/main 버전 기준 마이너 +1** 로 확정한다 (계획서 가정은 1.91.0).
7. 완료 후 `DEVLOG/2026-07-15-피드백-30-33-구현.md` 를 간단히 작성한다 — 계획서와 실제 코드가 달랐던 지점이 있으면 반드시 기록.
8. 작업 브랜치: main 최신에서 `fix/feedback-30-33` 분기. 완료 후 PR 을 생성하되 **머지는 하지 말 것**(한솔 승인 대기). PR 본문:
   - '업데이트 요약' 섹션은 비개발자 톤 — 계획서 작업 7의 update-notes 문구를 그대로 재사용해도 된다. 저장소의 `.claude/skills/pr-creator/SKILL.md` 구조를 따르면 더 좋다.
   - 계획서 부록 B-2(마이그레이션 라이브 적용 게이트)와 B-3(슬랙 워크플로 확인 체크리스트)를 PR 본문에 포함해 한솔이 배포 전에 볼 수 있게 한다.
9. 계획서 문서 자체(`DEVLOG/2026-07-15-피드백-30-33-*.md`)는 수정하지 않는다.

완료 보고에는 작업별 커밋 해시, 테스트 결과 수치(계획서 헤더의 기준선 대비), 건너뛰거나 계획과 달라진 부분을 포함할 것.
```

# 로그인 복구 검증 — v1.117.1

## 확인한 원인과 범위

- 신고 대상 세 계정은 서버에 존재하며 이름 중복이나 다른 유니코드 표기가 없었다. 계정 삭제·재생성은 하지 않았다.
- v1.110.1의 사용자 조회는 `select('*')`였다. 비밀번호 컬럼 읽기 제한 후 실제 anon API에서 이 요청이 `42501 / permission denied for table users`로 실패함을 확인했다. 공개 컬럼을 지정한 요청은 성공했다.
- 해당 구버전은 원격 조회 실패 시 PC에 저장된 목록으로 로그인 대상을 찾는다. 그 목록에 없는 실제 등록 사용자도 미등록으로 표시될 수 있다. 대상 PC 버전·로그가 확보되지 않았으므로 개별 PC의 발생 원인까지 확정했다고 보지는 않는다.
- 최신 앱은 공개 컬럼 조회와 `app_login` 서버 인증을 사용한다. 다만 서버 인증과 사용자 조회가 모두 실패하면 로컬 목록만 보고 미등록으로 잘못 표시하는 분기가 남아 있었다.
- 초기 비밀번호와 다르다는 결과는 계정 삭제나 미등록의 증거가 아니다. 서버 연결 문제와 비밀번호 불일치를 구분했다.

## 수정

- `SessionManager.verifyCredentials()`에서 디렉터리의 `status`를 유지한다. 정본에서 이름이 없을 때만 미등록으로 안내하고, 불완전한 로컬 목록이면 연결·업데이트 확인 안내를 표시한다.
- 서버의 비밀번호 거절은 그대로 최종 실패다. 기존 로컬 비밀번호 대조 및 서버 토큰 경계는 변경하지 않았다. 서버 비밀번호 읽기 권한을 다시 열지 않았다.
- 로그인 화면에 현재 버전·업데이트 내역 진입을 추가했다. 기존 모달을 로그인 전에도 연결하고, 사용자가 새로고침·준비된 업데이트 적용을 할 수 있도록 했다. 모달을 여는 것만으로 자동 조회하지 않는다.

## 계정 복구 확인

- 사용자 승인 범위의 두 계정에만 비밀번호 초기화를 적용했다. 다른 한 계정의 비밀번호는 변경하지 않았다.
- 먼저 동일 작업을 트랜잭션에서 시험하고 롤백한 뒤 실제 적용했다. ID와 계정 메타데이터가 유지됐으며 씬·개인 할 일·메모·캘린더 일정·간트 프로젝트의 데이터 지문이 변경 전후 일치했다.
- 실제 anon HTTP API와 수정된 SessionManager를 함께 사용한 세 계정 로그인 검증이 성공했다. 기존 사용자 ID와 서버 토큰 발급, renderer 응답의 비밀번호·토큰 비노출을 확인했다.
- 검증용 세션은 해당 세션만 만료시켰다. 계정이나 작업 데이터 삭제는 하지 않았다.

## 검증

- 회귀 테스트: 수정 전 3개 실패 → 수정 후 로그인 인증 17개 통과.
- 로그인 전 업데이트 테스트: 수정 전 진입/mount 관련 4개 실패 → 수정 후 5개 통과. 열기·수동 새로고침·적용 handler와 splash 제외를 검증했다.
- `npm run typecheck`, `npm run build:vite`: 통과. 전체 2,499개 중 2,471개 통과, 28개 기존 환경 의존 skip, 실패 0개.
- 독립 Chrome 프리뷰: 로그인 전 버전 버튼→모달 열기→수동 새로고침→닫기→테스트 계정 로그인→대시보드까지 확인했다.
- 실제 사용자 PC의 설치·재시작·로그인은 별도 운영 확인 대상이다. 프리뷰나 서버 API 성공을 해당 PC의 E2E 성공으로 간주하지 않는다.

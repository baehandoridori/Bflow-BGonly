# PR Creator

GitHub PR을 체계적이고 읽기 쉽게 작성하는 스킬.

이 스킬의 핵심 목적은 두 가지다:
1. **PR 자체가 변경 기록이 되게** — 나중에 "이 버전에서 뭐 바꿨지?" 할 때 PR만 보면 알 수 있도록
2. **코드를 모르는 사람도 읽을 수 있게** — PR 본문이 슬랙으로 공유되어 비개발자 동료도 업데이트 내용을 파악할 수 있도록

---

## PR 작성 프로세스

### 1단계: 현재 상태 파악

PR 작성을 요청받으면, 먼저 아래 정보를 수집한다.

**브랜치 확인:**
```bash
git branch --show-current
git log --oneline main..HEAD
```

**최신 태그 확인:**
```bash
git describe --tags --abbrev=0 2>/dev/null || echo "태그 없음"
```

**태그 이후 커밋 내역 수집:**
```bash
git log $(git describe --tags --abbrev=0 2>/dev/null || git rev-list --max-parents=0 HEAD)..HEAD --oneline --no-merges
```

**변경된 파일 목록:**
```bash
git diff --stat main..HEAD
```

태그가 아예 없는 프로젝트라면 전체 커밋을 기준으로 분석하되, 버전은 `v0.1.0`부터 시작하도록 제안한다.

### 2단계: 버전 추론

커밋 메시지의 prefix를 분석해서 다음 버전을 제안한다. Semantic Versioning(major.minor.patch) 규칙을 따른다:

| 커밋 prefix | 버전 영향 | 설명 |
|-------------|----------|------|
| `feat:` | **minor** 올림 | 새 기능 추가 |
| `fix:` | **patch** 올림 | 버그 수정 |
| `refactor:`, `chore:`, `style:`, `docs:`, `perf:` | **patch** 올림 | 내부 개선 |
| `BREAKING CHANGE` 또는 `!` 포함 | **major** 올림 | 호환성 깨지는 변경 |

여러 종류가 섞여 있으면 가장 높은 영향을 기준으로 한다. 예: feat + fix가 둘 다 있으면 minor를 올린다.

**제안 형식:**
```
현재 최신 태그: v1.3.2
커밋 분석: feat 2건, fix 3건
→ 제안 버전: v1.4.0
```

사용자가 다른 버전을 원하면 그걸 따른다. 현재 대화에서 PR 생성 권한이 명시되어 있으면 버전 제안 뒤에도 별도 확인 없이 PR을 생성한다.

### 3단계: PR 제목 작성

**형식:**
```
[v버전] 변경 내용 한 줄 요약
```

**규칙:**
- 버전 태그를 대괄호로 감싼다
- 요약은 "~를 추가/수정/개선" 형태로, 핵심 변경사항 1~2개만 언급
- 50자 이내 권장 (GitHub에서 잘리지 않도록)

**좋은 예:**
```
[v1.4.0] 프레임 네비게이션 개선 및 드로잉 도구 추가
[v2.0.0] mpv 엔진 교체로 재생 시스템 전면 개편
[v1.3.1] 구글 드라이브 동기화 오류 수정
```

**나쁜 예:**
```
[v1.4.0] 여러 가지 수정  ← 뭘 수정했는지 모름
[v1.4.0] feat: add frame navigation and fix drawing tool bug  ← 영어, prefix 불필요
Update  ← 버전 없음, 내용 없음
```

### 4단계: PR 본문 작성

본문은 반드시 아래 4개 섹션 순서대로 작성한다.

---

#### 섹션 1: 📋 업데이트 요약

이 섹션의 독자는 **코드를 모르는 실사용자**다. 슬랙에 그대로 공유될 수 있다고 생각하고 쓴다.

**원칙:**
- 기술 용어를 쓰지 않는다. "컴포넌트 리팩토링" 대신 "화면 구성을 더 깔끔하게 정리"
- "뭐가 바뀌었고, 사용자 입장에서 뭐가 달라지는지"를 쓴다
- 코드 변경이 사용자에게 영향이 없는 경우 (내부 리팩토링 등), 그래도 체감할 수 있는 변화가 있다면 언급한다 (예: "앱이 좀 더 빨라졌어요")
- 이모지를 활용해 변경 유형을 직관적으로 표시한다

**형식:**
```markdown
## 📋 업데이트 요약

> 이번 업데이트에서 달라진 점을 간략하게 정리했습니다.

- ✨ 새 기능: [사용자가 이해할 수 있는 설명]
- 🐛 버그 수정: [어떤 문제가 해결됐는지]
- ⚡ 개선: [뭐가 나아졌는지]
```

**예시:**
```markdown
## 📋 업데이트 요약

> 이번 업데이트에서 달라진 점을 간략하게 정리했습니다.

- ✨ 영상 위에 직접 그림을 그릴 수 있는 드로잉 도구가 추가됐습니다
- 🐛 프레임 이동할 때 가끔 1프레임 밀리던 문제를 수정했습니다
- ⚡ 영상 로딩 속도가 약 40% 빨라졌습니다
```

#### 섹션 2: 🔧 상세 기술 설명

이 섹션의 독자는 **개발자 또는 미래의 자신**이다. 코드 수준에서 뭘 바꿨는지 기록한다.

**원칙:**
- 파일명, 함수명, 구체적인 구현 방식을 포함한다
- 커밋 내역을 기반으로 하되, 단순 커밋 나열이 아닌 논리적으로 묶어서 설명한다
- 왜 이 방식을 선택했는지 맥락을 포함한다

**형식:**
```markdown
## 🔧 상세 기술 설명

### [변경 카테고리 1]
- 구체적인 변경 내용과 이유
- 관련 파일: `경로/파일명`

### [변경 카테고리 2]
- ...
```

**예시:**
```markdown
## 🔧 상세 기술 설명

### 드로잉 시스템 추가
- Canvas 기반 드로잉 레이어를 mpv 렌더링 위에 오버레이로 구현
- `src/renderer/drawing/` 디렉토리에 DrawingCanvas, BrushEngine, StrokeHistory 추가
- 실시간 협업을 위해 Liveblocks의 Storage API와 연동
- Undo/Redo는 커맨드 패턴으로 구현 (`StrokeHistory.ts`)

### 프레임 네비게이션 정확도 개선
- mpv의 `frame-step` 명령 대신 `seek` + `pts` 기반으로 전환
- 기존 방식은 VFR(가변 프레임레이트) 영상에서 1프레임 오차 발생
- 관련 파일: `src/renderer/player/FrameNavigator.ts`
```

#### 섹션 3: 🚧 개발 난항

커밋 내역에서 시행착오 흔적(revert, 반복 수정, 긴 시간 간격 등)을 분석해 개발 과정에서 어려웠던 점을 기록한다.

이 섹션의 목적은 **같은 실수를 반복하지 않기 위한 기록**이다.

**분석 기준:**
- 같은 파일을 여러 번 수정한 커밋 → 삽질 가능성
- `revert`, `fix`, `hotfix` 등이 연속으로 나타남
- 커밋 메시지에 "다시", "재시도", "다른 방법" 같은 키워드
- 한 커밋에서 대량의 파일 변경 → 대규모 구조 변경 시도

**형식:**
```markdown
## 🚧 개발 난항

### [문제 제목]
- **문제**: 무엇이 어려웠는지
- **시도**: 어떤 접근을 했는지
- **해결**: 최종적으로 어떻게 해결했는지
- **교훈**: 다음에 참고할 점
```

난항으로 볼 만한 내용이 커밋에 없으면:
```markdown
## 🚧 개발 난항

특이사항 없음
```

#### 섹션 4: ✅ 테스트 가이드

두 파트로 나눈다: 실사용자용과 개발자용.

**형식:**
```markdown
## ✅ 테스트 가이드

### 사용자 테스트
> 아래 시나리오를 직접 실행해서 정상 동작을 확인해주세요.

1. **[기능 이름]**
   - [구체적인 실행 단계]
   - ✅ 기대 결과: [정상이면 이렇게 보임]
   - ❌ 비정상: [문제가 있으면 이렇게 보임]

### 개발자 테스트
```bash
# 전체 테스트
npm test

# 특정 모듈 테스트
npm test -- --grep "FrameNavigator"
```
> 추가 확인 사항: [수동으로 확인해야 할 엣지 케이스]
```

**사용자 테스트 원칙:**
- 클릭 몇 번으로 확인 가능한 시나리오
- 스크린샷이 필요하면 기대 화면을 텍스트로 묘사
- 기술 용어 대신 "이 버튼 누르면", "이 화면에서" 같은 표현

**개발자 테스트 원칙:**
- 실행 가능한 명령어 제공
- 테스트가 없는 변경사항이면, 수동 확인 방법을 적는다
- 프로젝트에 테스트 프레임워크가 없으면 이 파트를 생략하고 사용자 테스트만 작성

## PR 생성 실행

본문 작성이 완료되면 현재 대화에서 PR 생성 권한이 이미 명시되어 있는지 확인한다. 권한이 명시되어 있으면 제목과 본문을 기록으로 남기고 사용자에게 재확인을 받지 않고 바로 생성한다.

사용자에게 묻지 말고 리포지토리의 기본 브랜치를 먼저 확인한다:

```bash
BASE_BRANCH=$(gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name')
```

확인한 기본 브랜치를 `--base`에 넣어 `gh pr create`를 실행한다:

```bash
gh pr create \
  --title "[제목]" \
  --body "[본문]" \
  --base "$BASE_BRANCH"
```

---

## 주의사항

- **승인된 PR 요청은 바로 생성** — 현재 대화에서 PR 생성 권한이 명시되어 있으면 별도 확인을 받지 않고 `gh pr create` 실행
- **커밋이 없으면 PR을 만들 수 없다** — `git log main..HEAD`가 비어있으면 "커밋이 없어서 PR을 만들 수 없습니다"라고 안내
- **충돌 상태 확인** — merge conflict가 있으면 먼저 해결하도록 안내
- **draft PR 옵션** — 사용자가 원하면 `--draft` 플래그 추가
- **이 스킬은 PR "작성"이 핵심이지, PR 리뷰나 머지는 다루지 않는다**
